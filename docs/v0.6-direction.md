# v0.6 方向：B 方案（主管 → 员工）

2026-11-15。这份文档记录和用户逐场景核对后确认的需求，以及参考 agent-autoloop、DeepSeek Super-Agent、LobeHub 后定下的设计。它优先于 `PLAN.md` 中与之冲突的部分。产品定位：以 Paperclip 为底座的个人产品，不开源、不商用。

## 确认的日常场景

| # | 场景 | 要的行为 |
| --- | --- | --- |
| 1 | 丢一句话就走 | 主管理解意图：小事直接派，大事先给计划等批准 |
| 2 | 科研全流程 | 读论文 → 判断能否用于课题 → 设计实验 → 跑实验 → 分析，一名员工从头做到尾 |
| 3 | 长时间实验 | 本机或远程服务器，几分钟到过夜；跑完或出错时员工自己回来接着处理 |
| 4 | 只在必要时被打断 | 结果与预期不符、要花大钱或长时间、要改动重要东西、反复失败卡住 |
| 5 | 交付 | 一页结论加证据，过程折叠 |
| 6 | 几件不相关的事同时进行 | 各主管、各员工互不干扰 |
| 7 | 各领域有自己的专家 | 主管、员工由用户命名，各有记忆、技能、MCP 和模型；不预设科研 / 公司 / 生活 |
| 8 | 主动盯守 | 邮件、新闻和新论文、实验状态，有情况才通知 |
| 9 | 越用越懂用户 | 全局"关于我"和决定记录 |
| 10 | 界面 | 输入框、待决定卡片、任务进展三块为主；简洁；外观可换 |

## 结构

| 角色 | 是什么 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 路由 | 一次便宜的模型调用（默认 Haiku），用户看不到 | 即时问答；按主管的领域选主管；识别"对已有任务的补充"并转给原主管 | 理解意图、做决定、改写用户的话 |
| 主管 | 用户命名，数量不限，默认 Opus 5.5，只能用 Claude | 理解意图、写任务书和验收标准、判断是否先出计划、选员工（或提议新建）、回答员工的问题、逐条验收、汇报、记录用户的长期决定、转交给别的主管 | 亲手干活 |
| 员工 | 用户命名，固定归属一名主管，Claude 或 Codex | 按任务书从头做到尾，逐条附证据交付；执行细节和上下文都留在员工这里 | 判定是否通过、结案、直接找用户 |

## 从三个参考项目吸收的做法

**DeepSeek Super-Agent / 知乎讨论：上下文拓扑**

- **"主管不干活"由架构保证，而不是靠提示词。** 消融实验表明，可选的委派工具在中性提示下几乎不会被用。所以主管的 Claude Code 只开放管理工具：`curl`、`jq`、阅读、搜索、编辑自己的 `memory/`；不跑 `--dangerously-skip-permissions`，用 `--allowedTools` 白名单，禁用 Task / Agent。见 `scripts/lib/department.mjs` 里的 `LEAD_TOOLS`。
- **每个任务一个干净会话。** Paperclip 按任务续接会话：主管每个需求一个上下文，员工每个子任务一个上下文。跨任务只通过记忆文件传递。
- **员工不直接对用户说话**：问题评论到父任务上，主管能答就答，答不了才转给用户。
- **递归委派**：员工可以在自己的会话里用子智能体，对主管透明；不在 Paperclip 里建子任务。

**LobeHub：验收是一等数据**

- 主管把验收标准写进任务书（`brief` 文档）。
- 员工逐条附证据，**只交证据、不判定通过**；可以对不合理的标准提出异议。
- 主管逐条判定：通过 / 未通过 / 无法判断。
- 记忆写入走"提议 → 审核 → 写入"（第 2 步）。

**agent-autoloop：决定记录和事件入口**

- 全局 `profile/user.md`（关于我）、`decisions.md`（定过的事）、`declined.md`（拒绝过的事）。所有主管自动加载，员工作为背景。用户说"以后都这样"时由主管追加，接口是 `POST /agentself/api/profile/decisions`。
- **两条入口**：用户随手说的话走"路由 → 主管 → 员工"；定时和事件类的活由规则直接派给员工，不叫醒主管，员工判断有事才通知用户。

## 一件事的流程

1. 用户说一句话，路由选出主管。任务描述是用户原话，后附路由说明。
2. 主管读全局档案和自己的记忆，写任务书（目标、背景、验收标准、不做什么、约束）。
   - 大事：用 `ask` 发计划，等同意。
   - 不归自己管：转给别的主管。
3. 主管从自己的员工里选一名，建一个子任务（任务书即描述），父任务设为等待它。
4. 员工干活。有问题就评论到父任务，主管回答或转问用户。长实验放后台，用 `later` 回来查。
5. 员工写 `report`，逐条附证据，然后置为 `done`。系统叫醒主管。
6. 主管逐条判定：
   - 全部通过：写一页报告，父任务置为 `in_review`。
   - 有不通过：打回一次；第二次仍不通过时，插件发卡片问用户。
7. 用户确认，任务结束。用户说"以后都这样"时，主管记进决定记录。

## 三步走

1. **结构和行为**（本次完成）：
   - 恢复主管层，主管工具受限。
   - 路由只选主管；两份技能按本方案重写。
   - 全局档案和决定记录，含设置页编辑。
   - 返工上限改为 2。
   - 向导不预设名字；示例团队移到验收脚本的 fixtures。
2. **规则**（本次完成）：
   - **结构化验收**：主管用 `team.criteria` 登记验收标准（编号 c1..cN，生成"验收标准"文档）；员工用 `team.evidence` 逐条交证据，可以提异议；主管用 `team.verify` 请独立核查员逐条判定，结果写成"独立核查"文档。核查员默认用 Sonnet（`verifierModel`），没有任何工具，只看标准、证据和报告。核查结果相同就复用，不重复调用。
   - **新建员工审批**：主管 `POST /agentself/api/hire-requests` 提议；首页出现"主管想新建员工"，可以改名后同意，系统自动建好（归属该主管、带技能和记忆），并在主管的任务上评论叫醒它。每位主管最多 3 条待批。
   - **可编辑的先问清单**：全局档案 `askfirst.md`，所有主管和员工自动加载，在设置里改。技能里不再写死四种情况。
   - **长实验看守**：员工用 `team.watch` 登记探测命令（0 = 结束，1 = 还在跑，其他 = 出错）。插件每分钟检查到期的看守，运行命令时不调用模型；结束、出错或超时才评论并叫醒员工。间隔 2–240 分钟，最长 72 小时。
   - **记忆写入改为提议 → 审核**：空闲整理时，对所有人都有用的用户偏好只生成提议（`profile/proposals.json`），在设置 → 关于我里确认后才写入；员工自己的 notes 仍直接写。
   - **定时盯守模板**：向导里提供"新论文 / 邮件 / 新闻"三个模板，直接派给员工，有情况才通知。
3. **界面**（2026-11-15，SETO 风格，规范见 `docs/handoff/design/DESIGN.md`）：
   - 办公室皮肤换成冷灰底、白色浮层、墨黑主操作、胶囊控件、衬线标题，深色模式完整；新增的 token 都是可选的，朝堂皮肤和第三方皮肤不受影响。
   - 侧栏四项（工作台 / 项目 / 主管 / 管理）+ 设置，全部换成线性图标；主管行用团队图标，像素机器人只代表员工。
   - 工作台三块：字标与理念、"待你处理"卡片（新建员工请求也作为卡片放进来，计入"要你拍板"）、固定在底部的输入框；右侧"任务进展"面板按主管分组，四段阶段条。
   - 卡片展开显示验收摘要（来自"验收标准"和"独立核查"文档）；拍板卡可勾选"以后同类直接这样做"，写进决定记录。
   - 项目抽屉、主管页、设置（分标签，"关于我"两栏 + 记忆提议卡）按规范重做；像素办公室换新调色板，主管工位加渐变描边。

## 本机实测后的修正（2026-11-15）

P1 实测发现三个问题，已修：

- **主管在 Windows 上调不通接口。** Claude Code 在 Windows 上用 PowerShell 工具执行命令，`Bash(curl:*)` 永远匹配不上。现在主管完全不用命令行：新增团队 MCP 服务 `apps/console/server/mcp-team.mjs`，提供主管要做的每件事（读任务、写文档、派活、评论、改状态、发卡片、验收标准、核查、提议新建员工、记决定）。主管白名单只剩 `mcp__agentself`、读文件、上网和自己的 `memory/`，并显式禁用 Bash、PowerShell、Task、Agent。派活的 `create_subtask` 只能派给自己的员工，并会自动让父任务等待子任务。
- **主管技能在 CLI 引擎下加载失败**（"Unknown skill"）。主管技能改为写进工作目录的 `.agentself/lead-skill.md`，由 `CLAUDE.md` 导入，不再依赖 Paperclip 挂载技能。
- **旧的 `.claude/settings.local.json` 扩大了白名单。** 主管工作目录里的这个文件现在由 Agentself 接管（旧文件备份为 `.bak`），只放行团队 MCP、禁用所有命令行。
- **`team.verify` 超时**（Paperclip 调插件工具默认只等 30 秒）。改为异步：第一次调用在后台开始核查并立即返回；核查完成后在主管的任务上留言叫醒主管，再调用一次拿逐条结果。核查进行中重复调用不会再起一次模型。

### 第二轮实测（AGE-108 / AGE-109）：员工被放进了主管目录

Paperclip 的设计是子任务沿用父任务的执行工作区（`server/src/services/issues.ts` 里建任务时的继承逻辑，除非显式指定工作区）。所以员工会在主管的目录里运行，读到主管目录里的 `CLAUDE.md`（主管身份）和 `.claude/settings.local.json`（禁用命令行）。

结论：**凡是属于某个智能体的东西，都不能放在工作目录里**，要跟着智能体自己的配置走。

- **身份、技能、记忆位置**：每个智能体一份 `.agentself/instructions.md`（技能全文 + 记忆和全局档案的绝对路径），通过 Paperclip 的 `instructionsFilePath` 注入每次运行，不管在哪个目录。旧版本写进 `CLAUDE.md` / `AGENTS.md` 的身份块会被清掉，用户自己的内容保留。
- **权限和 MCP**：只放在命令行参数里（`--allowedTools` / `--disallowedTools` / `--mcp-config`）。主管目录里的 `.claude/settings.local.json` 改成中性文件，既不放宽也不收紧，旧文件备份为 `.bak`。主管写记忆的规则改用绝对路径。
- **Claude 员工也切到 CLI 引擎**：`instructionsFilePath` 和命令行参数只在 CLI 引擎下生效，ACP 引擎会提前返回、全部忽略。员工保留所有工具，并挂上团队 MCP 服务（员工角色），Windows 上不再需要 curl。Codex 员工只用指令文件（Paperclip 没有给 Codex 挂 MCP 的参数），仍用 `curl.exe`。
- **不改 Paperclip 核心**：沿用父任务工作区反而有好处，主管能直接读到员工的产物。代价是员工的产物会落在主管的工作目录里。

本地服务启动时会自动同步所有 Agentself 智能体的运行环境（指令文件、MCP 配置、adapter 配置、清理旧文件），也可以 `POST /agentself/api/agents/sync` 手动触发，已有的主管和员工不用重建。

P1 验收脚本已按新流程改写：一名员工、任务书和验收标准、证据、独立核查、汇报，全部满足才算 PASS。

### 第三轮实测（AGE-111 / AGE-112）：主流程跑通，核查和任务书两项未过

- **后台核查每次 1 秒内失败**：插件工具调用返回后，这次调用的授权范围就失效了，后台再调宿主接口全部被拒。改为：所有宿主读取都在工具调用内完成；核查员作为普通子进程运行，结果写到本地文件（`~/.agentself/verify/`）；每分钟一次的 `verify-tick` 任务用它自己的授权范围记录结果、写"独立核查"文档、留言叫醒主管。宿主写入失败会保留文件、下一分钟重试，最多 5 次。核查失败后，主管再调用会拿到失败原因，不会悄悄重跑。
- **主管没写任务书**：`create_subtask` 在父任务还没有 `brief` 时，会把任务书同时存为父任务的 `brief`；主管技能也强调了任务书必须写。
- **可观测性**：插件日志把错误写进消息正文（Paperclip 日志不显示额外字段）；启动同步每次失败都会打印原因，最多重试约 5 分钟。
- **`issue_disposition_repair` 唤醒**：主管技能新增"每一轮结束时父任务必须处于明确的等待状态"，并列出四种合格状态。
- `memory.test.ts` 的整理用例超时上限放宽到 20 秒。

### 第四轮实测：P1 通过，P4 未过

P4 里任务 A 把偏好写进了员工记忆，任务 B 却完全没读记忆文件：指令文件只给了路径，简单任务上模型就跳过了。改为把**内容**直接放进指令文件（`scripts/lib/instructions.mjs`）：全局档案四份文件、员工的 identity / style / user / notes 全文（各有长度上限，超出时注明完整文件位置），以及主题资料的文件列表。内容一变就重新生成：

- 每次运行结束后（插件，智能体可能刚写过记忆）；
- 空闲整理和每周归档之后（插件）；
- 用户在网页上改记忆、改全局档案、确认记忆提议，或主管记下决定时（本地服务；全局档案变化会刷新所有智能体）。

顺便修掉的缺口：员工的 `notify_user` 和记忆整理的提醒以前只存进插件状态，工作台从没显示过。现在工作台读取插件的 `notices`，显示为"通知"卡片（计入"交付结果"），点"知道了"会通过插件动作 `notice-dismiss` 标为已处理。

还没做、也还不能验收的：

- **远程机器上的长实验**：要先定发布形态（主机 + 执行机，见发布讨论），再验证 Paperclip 的 SSH 执行环境。
- **邮件盯守**：需要先接邮箱连接器（MCP）；p15 用本地文件代替收件箱。
- **飞书推送**：新建员工的请求和通知不推送到飞书。
- **Codex 员工**：没有团队 MCP 工具，仍用 `curl.exe`；独立核查员不能选 Codex。
- **项目抽屉里的看守信息**：需要插件提供查询接口。
- **中文字体**：中文衬线和黑体仍用系统字体。
