# v0.6 方向：B 方案（主管 → 员工）

2026-11-15。这份文档记录和用户逐场景核对后确认的需求，以及参考 agent-autoloop、DeepSeek Super-Agent、LobeHub 后定下的设计。它优先于 `PLAN.md` 中与之冲突的部分。产品定位：以 Paperclip 为底座的个人产品，不开源、不商用。

## 确认的日常场景

| # | 场景 | 要的行为 |
| --- | --- | --- |
| 1 | 丢一句话就走 | 主管理解意图：小事直接派，大事先给计划等批准 |
| 2 | 科研全流程 | 读论文 → 判断能否用于课题 → 设计实验 → 跑实验 → 分析，一名员工从头做到尾 |
| 3 | 长时间实验 | 本机或远程服务器，几分钟到过夜；跑完或出错时员工自己回来接着处理 |
| 4 | 只在必要时被打断 | 结果与预期不符、要花大钱或长时间、要改动重要东西、反复失败卡住 |
| 5 | 交付 | 一页结论加证据，过程折叠 |
| 6 | 几件不相关的事同时进行 | 各主管、各员工互不干扰 |
| 7 | 各领域有自己的专家 | 主管、员工由用户命名，各有记忆、技能、MCP 和模型；不预设科研 / 公司 / 生活 |
| 8 | 主动盯守 | 邮件、新闻和新论文、实验状态，有情况才通知 |
| 9 | 越用越懂用户 | 全局"关于我"和决定记录 |
| 10 | 界面 | 输入框、待决定卡片、任务进展三块为主；简洁；外观可换 |

明确不要的：把一件事切给多人并行。

## 结构

| 角色 | 是什么 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 路由 | 一次便宜的模型调用（默认 Haiku），用户看不到 | 即时问答；按主管的领域选主管；识别"对已有任务的补充"并转给原主管 | 理解意图、做决定、改写用户的话 |
| 主管 | 用户命名，数量不限，默认 Opus 5.5，只能用 Claude | 理解意图、写任务书和验收标准、判断是否先出计划、选员工（或提议新建）、回答员工的问题、逐条验收、汇报、记录用户的长期决定、转交给别的主管 | 亲手干活 |
| 员工 | 用户命名，固定归属一名主管，Claude 或 Codex | 按任务书从头做到尾，逐条附证据交付；执行细节和上下文都留在员工这里 | 判定是否通过、结案、直接找用户 |

## 从三个参考项目吸收的做法

**DeepSeek Super-Agent / 知乎讨论：上下文拓扑**

- **"主管不干活"由架构保证，而不是靠提示词。** 消融实验表明，可选的委派工具在中性提示下几乎不会被用。所以主管的 Claude Code 只开放管理工具：`curl`、`jq`、阅读、搜索、编辑自己的 `memory/`；不跑 `--dangerously-skip-permissions`，用 `--allowedTools` 白名单，禁用 Task / Agent。见 `scripts/lib/department.mjs` 里的 `LEAD_TOOLS`。
- **每个任务一个干净会话。** Paperclip 按任务续接会话：主管每个需求一个上下文，员工每个子任务一个上下文。跨任务只通过记忆文件传递。
- **员工不直接对用户说话**：问题评论到父任务上，主管能答就答，答不了才转给用户。
- **递归委派**：员工可以在自己的会话里用子智能体，对主管透明；不在 Paperclip 里建子任务。

**LobeHub：验收是一等数据**

- 主管把验收标准写进任务书（`brief` 文档）。
- 员工逐条附证据，**只交证据、不判定通过**；可以对不合理的标准提出异议。
- 主管逐条判定：通过 / 未通过 / 无法判断。
- 记忆写入走"提议 → 审核 → 写入"（第 2 步）。

**agent-autoloop：决定记录和事件入口**

- 全局 `profile/user.md`（关于我）、`decisions.md`（定过的事）、`declined.md`（拒绝过的事）。所有主管自动加载，员工作为背景。用户说"以后都这样"时由主管追加，接口是 `POST /agentself/api/profile/decisions`。
- **两条入口**：用户随手说的话走"路由 → 主管 → 员工"；定时和事件类的活由规则直接派给员工，不叫醒主管，员工判断有事才通知用户。

## 一件事的流程

1. 用户说一句话，路由选出主管。任务描述是用户原话，后附路由说明。
2. 主管读全局档案和自己的记忆，写任务书（目标、背景、验收标准、不做什么、约束）。
   - 大事：用 `ask` 发计划，等同意。
   - 不归自己管：转给别的主管。
3. 主管从自己的员工里选一名，建一个子任务（任务书即描述），父任务设为等待它。
4. 员工干活。有问题就评论到父任务，主管回答或转问用户。长实验放后台，用 `later` 回来查。
5. 员工写 `report`，逐条附证据，然后置为 `done`。系统叫醒主管。
6. 主管逐条判定：
   - 全部通过：写一页报告，父任务置为 `in_review`。
   - 有不通过：打回一次；第二次仍不通过时，插件发卡片问用户。
7. 用户确认，任务结束。用户说"以后都这样"时，主管记进决定记录。

## 三步走

1. **结构和行为**（本次完成）：
   - 恢复主管层，主管工具受限。
   - 路由只选主管；两份技能按本方案重写。
   - 全局档案和决定记录，含设置页编辑。
   - 返工上限改为 2。
   - 向导不预设名字；示例团队移到验收脚本的 fixtures。
2. **规则**：
   - 新建员工审批工具（现在主管只能发卡片提议，由用户在向导里建）。
   - 可编辑的"先问清单"。
   - 验收证据和判定做成结构化数据，加独立核查者（不同模型）。
   - 长实验探测脚本：不调用模型，跑完才叫醒员工。
   - 记忆写入改为提议 → 审核。
   - 定时盯守模板。
3. **界面**：首页三块、侧栏四项、任务进展按主管分组、旧的部门概念收尾。

## 第 1 步的已知限制，需要在本机实测

- 主管的工具白名单依赖 Claude Code CLI 引擎（`engine: "cli"`）。Paperclip 默认的 ACP 引擎会忽略 `extraArgs`，所以主管强制用 CLI。需要确认：
  - 非交互模式下，白名单外的工具确实被拒绝；
  - Paperclip 若给智能体注入了 MCP 工具，主管还能调用。
- 员工在父任务上评论能否叫醒处于 `blocked` 状态的主管，需要实测；不能的话，第 2 步加插件兜底。
- "先出计划""四种打断条件"仍靠技能文字约束，第 2 步改为可编辑清单并尽量由插件兜底。
- 验收脚本 `p1-research`、`p2-console`、`p4-memory` 是按旧的部门流程写的，需要按新流程更新。
